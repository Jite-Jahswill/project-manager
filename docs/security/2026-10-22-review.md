# Security review: authentication, RBAC, tenant isolation, entitlements (2026-10-22)

Scope: the stage-1 foundation in `apps/api`, limited to authentication, platform RBAC, organization RBAC, branch-level access, field-level permissions, tenant isolation (application and database), and subscription entitlements. No business modules were added.

Method: code review of every guard, service and RLS policy, then a regression test per suspected issue, run against the **unfixed** code to confirm the issue was real before fixing it.

## Findings

| ID | Severity | Area | Finding | Confirmed by failing test | Fix |
|---|---|---|---|---|---|
| F1 | **High** | Org RBAC | **Privilege resurrection.** Revoking a membership kept its role assignments and overrides. Re-inviting the person (even as a viewer) reactivated the old membership, and every earlier role, e.g. Organization administrator, came back. Roles and overrides could also be attached to a revoked membership. | yes | Revocation removes all assignments and overrides (recorded in the audit event). Re-joining clears any residue. Role/override changes on revoked memberships return `409 membership_revoked`. |
| F11 | **High** | Org RBAC | **Authorization race.** RBAC mutations used the access snapshot taken by the guard *before* the organization lock. An admin demoted concurrently could still complete a role change queued behind the lock. | yes (deterministic lock test) | Every RBAC mutation locks the organization row, **re-loads the actor's access inside the lock**, re-checks the required permission, and uses that fresh access for all delegation and owner checks. |
| F5 | **High** | Platform / tenant isolation | **Platform admins could read tenants' business audit trail**, including before/after values of business records (product names, override reasons, invitation emails) via `/v1/platform/audit-events` and directly in platform DB scope. | yes | RLS: platform scope sees only identity/platform events (`organization_id IS NULL`) and actions performed by platform administrators. |
| F3 | Medium | Org RBAC | Invitations kept their power after the inviter was revoked or demoted, and couldn't be listed or withdrawn for 7 days. | yes | On acceptance, the inviter's **current** access is re-loaded and must still allow `organization.member.manage` and the delegation of the invited role. New `GET`/`DELETE /v1/orgs/:orgId/invitations[/:id]` (audited; token hashes never returned). |
| F2 | Medium | Entitlements | Member limit bypass: suspend a member → invite someone → reactivate the suspended member. Also, accepting an invitation after a plan downgrade wasn't re-checked. | yes (both) | Reactivation and invitation acceptance both run `assertBelowLimit(limit.members)` under the organization lock. |
| F7 | Medium | DB policy | Plans, prices, entitlements and platform RBAC tables were writable by the runtime role **from any context**. A bug or injection in tenant code could raise every plan's limits or create a platform admin. | yes (test changed 9 rows inside a rolled-back transaction) | RLS on those 7 tables: readable by the app role, writable only in platform scope. Bootstrap CLI sets platform scope. |
| F8 | Medium | DB policy / entitlements | An organization's own context could insert an `ACTIVE` enterprise subscription. | yes | Org-context inserts limited to a `TRIALING` subscription of at most 31 days; everything else needs platform scope. |
| F6 | Low | DB policy | Inside organization A's context, the user's memberships in **other** organizations (and those organizations' rows) were visible. Not reachable through current code, but it weakened RLS as a backstop. | yes | The "own memberships" exemption applies only when no organization context is set (the org switcher). |
| F10 | Low | Branch access / UI consistency | Organization-scoped permissions in a role assigned at a branch were silently ignored. A branch cashier or storekeeper couldn't read the product catalog the role editor showed them as having. | yes | Explicit `branchAssignable` flag on 5 non-sensitive catalog reads (unit test enforces: org-scoped, STANDARD, `read`). All other org-scoped permissions still don't apply through branch assignments, and the API now reports them (`notAppliedAtBranch` on role listings and assignment responses). |
| F12 | Info | Org RBAC | A member removing their own DENY override was blocked only incidentally (by the delegation rule). | no (already blocked) | Explicit self-check added. |
| F9 | Info | DB privileges | Runtime role has no `CREATE` on `public`; this relied on PostgreSQL 15+ defaults. | no (already safe) | Explicit `REVOKE` in migration; test kept. |

All fixes: `prisma/migrations/20261022090000_security_review_hardening`, `src/organizations/access-control.service.ts`, `src/authz/permission-{registry,evaluator}.ts`, `src/platform/bootstrap.ts`.

## Areas reviewed with no defect found

- **Authentication.**
  - Generic errors for unknown email, wrong password, locked or disabled accounts.
  - Dummy-hash timing equalization.
  - Refresh rotation with reuse detection and a race-safe conditional claim.
  - Session checked on every request.
  - Password reset revokes all sessions.
  - Cookie auth requires the CSRF header on unsafe methods.
  - Tokens carry no privileges.
- **Platform RBAC.** Separate registry, tables and guard. Privileged permissions need step-up. A suspended admin has no access. The bootstrap path is single-use and race-protected.
- **Delegation.** A non-owner can't grant, assign, revoke or edit permissions they don't hold, including combinations of branch-limited and org-wide holdings (unit-tested).
- **Validation.** Unknown body fields are rejected, and all route params are UUID-validated.

## Evidence (tests added in this review)

- `test/review-regressions.e2e-spec.ts`: 14 tests, one or more per finding. 11 of the 13 written first failed on the unfixed code; the 14th (downgrade) was confirmed by removing its fix and watching it fail.
- `test/authorization-matrix.e2e-spec.ts`: 16 generated sweeps over **every discovered route**.
  - Org A's owner → every route under B's URL, all methods: 403.
  - Org A's owner → every resource route under A's URL using B's IDs: 403/404 only.
  - A byte-level fingerprint of all 13 of B's tenant tables, including its audit log, is unchanged afterwards.
  - Same from B to A.
  - Each platform role template is allowed exactly on the routes whose permission it holds and denied on all others.
  - A role-less admin and a suspended admin are denied everywhere.
  - A removed platform role stops working on the next request.
  - All platform roles combined get 403 on every org route.
  - The platform audit view contains no tenant business events.
  - Mutation-tested: planting a guard bypass makes 4 of these tests fail.
- `test/rls.e2e-spec.ts` (+2):
  - A sweep generated over every table with `organization_id` finds zero rows of B in A's context.
  - A policy lint checks every tenant-table policy: bound to `ventidoc_app`, keyed on the tenant context, never `true`, and no business table readable in platform scope.
- `src/authz/permission-evaluator.spec.ts` (+3): branch-limited assignments never confer org administration. 500 generated access states show the permission list sent to the UI is exactly what `can()` enforces.

## Remaining limitations (not fixed in this review)

1. **[Superseded: largely addressed by the security gate, see [2026-10-22-security-gate.md](2026-10-22-security-gate.md#b-wrong-tenant-context-root-cause-fix-and-what-remains)]** **RLS can't catch an authorization bug that selects the wrong tenant.** If application code opens a tenant context for an organization the user isn't authorized for, RLS faithfully serves that organization. The mutation test demonstrated this. The mitigation is structural: only `OrgAuthzService` can produce the `EffectiveAccess` that `TenantDb.inOrg` accepts, `inOrgUnchecked` has 3 audited call sites, and the sweeps run in CI. Tenant context is a session GUC, so SQL injection could also change it; all SQL is parameterized and `$queryRawUnsafe` is lint-banned.
2. **[Resolved for the application role: see [2026-10-22-security-gate.md](2026-10-22-security-gate.md#a-password-hash-exposure-resolved-for-the-application-role)]** **Identity tables (`users`, `sessions`, tokens) have no RLS.** The runtime role could read every user's password hash. Recommended next: move credential reads behind a `SECURITY DEFINER` function owned by a separate role, and revoke column access to `password_hash`.
3. **Field-level permissions have no consumer yet.** No current endpoint returns restricted fields; HR/payroll/finance aren't built. Design: separate permission (`hr.employee.read_sensitive`) and separate DTOs or endpoints. **Audit events for restricted resources must store references, not values**, or `security.audit.read` holders will see salaries in before/after diffs.
4. **[Fixed in stage 2A: see [rate-limiting-and-abuse-protection.md](rate-limiting-and-abuse-protection.md)]** **Account lockout can be triggered by anyone who knows an email** (5 bad attempts → 15 min lock, doubling). This is a deliberate trade-off against brute force; MFA plus risk-based throttling should replace it.
5. **Step-up re-authentication is satisfied by any fresh login** for 10 minutes, and organization-level sensitive actions (role changes, ownership) don't require step-up yet. MFA isn't implemented.
6. **Unlimited organizations (and trials) per user.** Needs a product decision (owned-organization cap or verification for additional trials).
7. **Archiving products frees `limit.products` slots.** This is the current definition of the limit ("active catalog"); confirm it's the intended product semantics.
8. **[Fixed in stage 2A, pending production Redis/proxy configuration]** **Rate limiting is in-memory and per-IP** (single instance, no proxy trust). Redis storage and proxy configuration are required before scaling out. The API still refuses `NODE_ENV=production`.
9. The **guard's membership snapshot** is still used, without re-reading under a lock, for non-RBAC writes (products, stock, branches). Their window is a single request; RBAC changes, the only place where escalation matters, are now race-free.
10. Files, exports, background jobs and WebSockets don't exist yet, so mandatory tests 2 and 7 (those parts) remain pending.
11. CI (`.github/workflows/ci.yml`) hasn't been run on GitHub; all results above are from local runs.
